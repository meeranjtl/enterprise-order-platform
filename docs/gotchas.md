# Gotchas Ledger

Hard-won, non-obvious failure modes discovered during implementation — each cost real debugging time and won't be re-derived from reading the code. Compressed one-entry-per-issue; full narrative and validation evidence for each is in the linked `PHASE_N_COMPLETE.md`. Add new entries here when closing a phase — don't re-narrate them in `AGENTS.md`.

## Phase 9 — Shipping & Notification

- **MapStruct: never use `MappingConstants.ComponentModel.SPRING`** in `@Mapper` — with this repo's Lombok/MapStruct processor setup it silently fails Spring bean registration at runtime (`No qualifying bean of type ...Mapper`, service won't start). Always use the literal `@Mapper(componentModel = "spring")`.
- **Docker healthcheck timings matter under cold-start load**: kafka CLI probe needs `timeout: 20s`; schema-registry needs `start_period: 150s+`; service Dockerfile `HEALTHCHECK`s need `--start-period=180s` (JVM startup ~120s). Keep these windows when adding a service.
- **Surefire test discovery**: includes are `**/*Test.java`, `**/*Tests.java`, `**/*IT.java`. Repo convention is `XxxIT.java` / `class XxxIT` for integration tests (see `OrderServiceIT`, `CustomerServiceIT`) — a differently-named integration test silently never runs.

## Phase 10 — Analytics & Reporting

- **Spring Data JPA aggregate JPQL `SELECT`s always return `List<Object[]>`**, even for a guaranteed single row. Declaring the repository method to return a bare `Object[]` produces a nested-array `ClassCastException` at runtime — invisible to unit tests that mock the repository, only surfaces under a real query.
- **SQL `SUM(CASE...)` over zero matching rows is `NULL`, not `0`.** Wrap every conditional `SUM` in `COALESCE(..., 0)` unless the field should legitimately render as JSON `null` (e.g. an `AVG` with no contributing rows).
- **`localhost:9092` vs `localhost:9094`**: a JVM running directly on the host (not in a container) must use `9094` (`KAFKA_ADVERTISED_LISTENERS` → `PLAINTEXT_HOST`); `9092` only works from inside the compose network. Silent failure — the consumer just never receives anything, no error thrown.
- **Creating a product via product-service does not provision an inventory-service record.** An order against a freshly-created product fails reservation (`Inventory not found with identifier: N`) and sticks at `PENDING`. Pre-existing platform gap, not phase-specific — use a product with a seeded inventory row (id 1 or 2), or call `/api/v1/inventory/adjust` first, for E2E testing.
- **Gateway route wiring for a new service touches 5 places** — see [domain-rules.md](domain-rules.md#gateway-route-wiring-addingchanging-a-route).

→ full detail: [PHASE_10_COMPLETE.md](../PHASE_10_COMPLETE.md)

## Phase 11 — Observability

- **A Spring profile's scalar property fully overrides the base value, not merges** — same silent-drop risk as the list-override gotcha above, but for scalars. Gateway's `application-docker.yml` must redeclare `management.endpoints.web.exposure.include` or `/actuator/prometheus` silently vanishes only in Docker (works fine locally).
- **Kafka-hop trace propagation is architecturally absent, not a config gap.** The transactional outbox pattern writes the event inside the original request's transaction, then a separate `@Scheduled` `OutboxPoller` publishes it later on an unrelated thread — there is no trace context to propagate from at publish time. Confirmed in Zipkin: every outbox-poller span is a root span with no parent. A real fix means storing `traceId`/`spanId` on the outbox row and restoring that span context in `OutboxPublisher.publishEvent()` — deferred, not yet done. `X-Correlation-Id` (propagated via Kafka headers already) remains the way to correlate a saga's logs across services in the meantime.
- **Never rebuild many Spring Boot service images concurrently on a resource-constrained Docker Desktop.** `docker compose up -d --build` across 8 services at once crashed the Docker Desktop engine (`docker version` itself returned a `500` from the daemon — confirmed broken, not just slow). Rebuild sequentially: `docker compose build <service>` one at a time.
- **Neither `kafka` nor `zookeeper` has a data volume.** If either gets into a bad state (e.g. a stale ZooKeeper `NodeExistsException` after an unclean shutdown), `docker compose rm -f zookeeper kafka` + `up -d` recreates them cleanly — no data loss to worry about.

## Phase 12 — Security

- **`Jwts.builder()....signWith(key)` (no explicit algorithm) auto-selects the strongest HMAC variant the key's byte length supports** — a long dev secret picks HS384 or HS512, not HS256. Every resource-server decoder in this platform is built via `NimbusJwtDecoder.withSecretKey(key).build()` / `NimbusReactiveJwtDecoder.withSecretKey(key).build()`, which **default to expecting HS256 specifically**. A mismatch signs a token that looks completely valid and round-trips fine against itself, but every other service's decoder silently rejects it (401 on every protected endpoint). Always pin the algorithm explicitly: `.signWith(key, Jwts.SIG.HS256)`.
- **`@PreAuthorize` denials don't reach `SecurityFilterChain`'s `.accessDeniedHandler(...)`.** `AccessDeniedException` from method security is thrown *inside* `DispatcherServlet`'s handler invocation — already past `ExceptionTranslationFilter` at the filter-chain level — so Spring MVC's own exception resolution (`GlobalExceptionHandler`, the `@RestControllerAdvice`) is what actually sees it. Without a dedicated `@ExceptionHandler(AccessDeniedException.class)` there, it falls through to the generic `Exception.class` catch-all and comes back as a 500, not a 403. The filter-level `.accessDeniedHandler(...)` only fires for denials that occur *in the filter chain itself*; this project's authorization is entirely `@PreAuthorize`-based, so the MVC-level handler is the one that actually matters. Caught by live E2E testing, not by any unit test — see next entry.
- **`@WebMvcTest` slices don't reliably enforce `@EnableMethodSecurity`'s `@PreAuthorize` AOP proxying** in this codebase's package layout, even though the same slice *does* correctly apply shared-library's filter-chain-level JWT authentication (missing/invalid token → 401 works fine in a slice). A role-mismatch test written against a `@WebMvcTest` slice silently returns 200 instead of 403 — not because authorization is broken, but because the slice's narrower context doesn't proxy the controller bean the same way a full application context does. Verified correct in the real app via live `docker compose` E2E testing (a non-owner customer JWT correctly got 403 against another customer's order/profile). Don't write a slice-level regression test asserting a 403 from `@PreAuthorize` — it can't reliably catch a regression either way; use a full-context (`@SpringBootTest` + `@AutoConfigureMockMvc`) or live E2E check instead.
- **Registering a second `KeyResolver` bean (`jwtKeyResolver` alongside the existing `ipKeyResolver`) breaks Spring Cloud Gateway's own actuator endpoint** (`GatewayControllerEndpoint`) — it autowires `KeyResolver` by type with no qualifier, so two candidate beans throws `NoUniqueBeanDefinitionException` at context startup (not at request time — the whole gateway fails to boot). Mark the one that should be the platform default `@Primary`.
- **The Phase 11 zookeeper/kafka stale-ephemeral-node gotcha recurs on every ungraceful Docker Desktop stop** (crash, host sleep, manual kill), not just a first-run fluke — `kafka` exits immediately with `KeeperException$NodeExistsException` because zookeeper still holds the broker's old ephemeral registration. Same fix every time: `docker compose rm -f zookeeper kafka` then `docker compose up -d`.
- **Refresh-token logout doesn't verify the presented token is the *current* one** — `AuthService.logout()` only checks the token's signature/expiry/type and extracts the subject, then blanks whatever refresh token is on file for that customer. A previously-rotated (already-superseded) but still unexpired refresh token can therefore still end the *current* session. Not a security hole (still requires a validly-signed token for that specific customer, so no cross-account access), just a looser-than-ideal check — acceptable for this project's single-active-session model, revisit only if multi-session support is ever added.

## Phase 13 — React UI

- **A browser's CORS preflight (`OPTIONS`) carries no `Authorization` header, and gateway's reactive `SecurityConfig` didn't permit it pre-auth** — `.anyExchange().authenticated()` 401'd every preflight to `/api/v1/**` before Spring Cloud Gateway's own `globalcors` filter ever got a chance to answer it with `Access-Control-Allow-*` headers. Every protected route silently failed CORS for a real browser client while working perfectly via `curl`/Postman (neither triggers a preflight) — this is exactly why it survived all of Phase 12's E2E validation undetected. Fixed by permitting `OPTIONS` pre-auth: `.pathMatchers(HttpMethod.OPTIONS, "/**").permitAll()` before the catch-all `.anyExchange().authenticated()` in `gateway/.../config/SecurityConfig.java`. The equivalent servlet-side `shared-library/.../config/SecurityConfig.java` likely has the same latent gap, but the UI never calls a servlet service directly (gateway-only), so it's undiscovered/unfixed — revisit if anything ever hits a service port directly from a browser.
- **`/api/v1/categories/**` (product-service's `CategoryController`) had no gateway route at all** — `/api/v1/products/**` existed, categories didn't, a pre-existing gap from whichever phase added `CategoryController` without a matching route. Silent failure per the gateway-route-wiring invariant (route just doesn't exist, no build error). Fixed by adding a `category-service` route in both `application.yml` and `application-docker.yml`, reusing the `productService` circuit breaker/fallback (same JVM, same failure domain — no new resilience4j instance needed).
- **This platform's full stack (9 JVMs + Kafka/ZooKeeper/Postgres/Redis/schema-registry) needs meaningfully more than 8GB for Docker Desktop's VM.** At 8GB, Postgres crash-looped from what looks like OOM kills (its own logs showed repeated "database system was not properly shut down; automatic recovery in progress" every 1-2 minutes) and `schema-registry`/`shipping-service` exited outright — not a code bug. Resolved by raising Docker Desktop's memory allocation to ~16GB. If bringing up the full stack (not just a couple of services), check available RAM first.
- **Docker Desktop's `prometheus`/`grafana` containers can fail with "the path ... is not shared from the host"** even though every other bind-mounted service (e.g. gateway's logback config) works fine — a per-path Docker Desktop file-sharing setting (Settings → Resources → File Sharing), not a compose/code issue. Neither is required for UI development; `docker compose up -d <explicit service list>` excluding them unblocks everything else.
- **Phase 12 broke order-service's two internal service-to-service calls, and nothing caught it until Phase 13's live UI testing.** `OrderService.createOrder()` synchronously calls `CustomerClient.getCustomer()` (validate the customer exists) and `ProductClient.getProduct()` (price each line item) via plain `RestClient` calls straight to customer-service/product-service — pre-Phase-8 pattern, kept intentionally for immediate-consistency needs, not a Kafka violation. Neither call ever carried an `Authorization` header. Once Phase 12 made those target endpoints require a JWT, both calls started failing with a real (but misleadingly generic) `400 BAD_REQUEST "Customer/Product validation failed for ID: N"` — `RestClientResponseException`'s 4xx branch swallows the actual 401 and rewraps it. **Every order creation was broken from the moment Phase 12 shipped**; it went undetected because Phase 12's own E2E validation tested ownership/RBAC on existing orders, never `POST /api/v1/orders` itself. Fixed by forwarding the *caller's own* bearer token from the inbound `HttpServletRequest` (via `RequestContextHolder`) onto both outgoing calls — correct here because order creation is `CUSTOMER`-only and a customer can only ever look up their own record / any authenticated user can read a product.
- **Reading a `@Lob` column outside an active Hibernate session throws `"Unable to access lob stream"`, and this only surfaces once you query the entity from a plain, non-transactional read path.** `OutboxEvent.payload` is `@Lob`-mapped (Postgres `TEXT`); the pre-existing `OutboxPublisher` never hit this because it always reads `payload` inside its own `@Transactional publishPendingEvents()` method. The new Kafka Events UI page (Phase 13) added `OutboxEventController.recent()` — a plain `@GetMapping` with no transaction — and mapping the fetched entities to DTO (which touches `payload`) threw this exact error in production the first time it ran. Fixed by marking the controller method `@Transactional(readOnly = true)`. General rule: any new read path over a `@Lob` field needs its own transaction even if it's "just a GET."
- **The `nginxinc/nginx-unprivileged:alpine` image resolves `localhost` to `::1` (IPv6) only, but nginx (per `ui/nginx.conf`) binds `0.0.0.0` (IPv4 only).** `HEALTHCHECK CMD wget -qO- http://localhost:3000/` therefore always failed with "connection refused" — nginx was serving requests correctly the whole time (confirmed via `curl` from the host and via `wget http://127.0.0.1:3000/` from inside the container), only the healthcheck's own DNS resolution was wrong. Always target `127.0.0.1` explicitly in a container healthcheck, never `localhost` — this class of bug is invisible from outside the container (the app works, `docker ps` just never reports `healthy`).
- **Root `.dockerignore`'s blanket `ui/` exclude (added in Phase 11/12 to keep the ~270MB `ui/node_modules` out of every Java service's build context) silently broke `ui/Dockerfile`'s own build** the moment one was added — Docker only reads the `.dockerignore` at the build *context* root (repo root here, since `ui/Dockerfile` `COPY`s paths like `ui/package.json`), so a `ui/.dockerignore` file has no effect and is dead configuration for this build context. Fixed by narrowing the root exclude to `ui/node_modules/` and `ui/dist/` specifically, keeping `ui/src` and friends visible to the build context.
- **Spring Cloud Gateway's `globalcors` config only covers Gateway's own routing engine, not any plain `@RestController` living in the same app.** Adding `SystemHealthController` (Phase 13, a local `@RestController`, not a gateway route) meant its CORS preflight came back with no `Access-Control-Allow-*` headers at all, even though every gateway-*routed* path worked fine — `spring.cloud.gateway.globalcors` only fires within Gateway's route-processing filter chain. The documented fix, `globalcors.add-to-simple-url-handler-mapping: true`, makes things worse, not better: it registers a `CorsConfigurationSource` bean that Spring Security's WebFlux auto-config detects and enforces *itself*, and once *any* `CorsWebFilter`/`CorsConfigurationSource` bean exists in the context, Security starts enforcing CORS globally using it — 403-ing every path that source doesn't explicitly cover (confirmed live: enabling the flag turned "missing headers on `/api/v1/system/health`" into "403 on `/api/v1/orders/1`" and every other previously-working route). The only combination that's actually safe is **one** Java-defined `CorsWebFilter` bean covering the whole app (`/**`, same policy as the old `globalcors` block) with `spring.cloud.gateway.globalcors` removed entirely — running both at once double-applies `Access-Control-Allow-*` headers, which browsers reject as invalid. See `CorsConfig.java` in the gateway module.
